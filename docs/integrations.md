# Внешние каналы: подготовка подключения

Проверка источников: 15 сентября 2026 года. В этом этапе работает **локальный демонстрационный приём**, а не подключённые каналы. Код не делает сетевых запросов провайдерам, не отправляет сообщения клиентам и не уведомляет менеджера. Наличие ключей в `.env` этого не меняет. `APP_MODE` принимает только `demo`.

## Telegram

Официальный источник: [Telegram Bot API](https://core.telegram.org/bots/api), разделы [setWebhook](https://core.telegram.org/bots/api#setwebhook), [Update](https://core.telegram.org/bots/api#update), [sendMessage](https://core.telegram.org/bots/api#sendmessage). Документация открыта и проверена.

Подготовлены:

- `POST /webhooks/telegram`, нормализация `update_id`, `message.chat.id`, `message.text`;
- приём только личных текстовых сообщений; групповые и неподдерживаемые события игнорируются;
- обязательная проверка `X-Telegram-Bot-Api-Secret-Token` до обработки;
- дедупликация по паре канал / `update_id`, сохранение ответа в демонстрационную исходящую очередь.

После отдельного разрешения владельца понадобятся бот, созданный через BotFather, его токен, публичный HTTPS endpoint и секрет webhook. В `setWebhook` передают `url`, `secret_token` и `allowed_updates=["message"]`; допустимы символы A–Z, a–z, 0–9, `_`, `-`, длина секрета 1–256. Не вставлять токен в браузер, логи или клиентский JavaScript.

Будущий отправитель должен вызывать официальный `sendMessage`, проверять `ok`, сохранять реальный `message_id`, учитывать `retry_after` при ограничении частоты и сетевые таймауты. При неоднозначном результате нельзя слепо повторять отправку: провайдер мог принять сообщение до обрыва связи. Для этого нужна отдельная очередь доставки и ручная проверка неопределённых результатов. В текущем прототипе отправителя нет; проверяется местный симулятор ошибки.

## Instagram

Выбран официальный путь **Instagram API with Instagram Login**, а не вход по паролю или автоматизация Direct. Ориентиры:

- [Messaging API — Meta](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api)
- [Webhooks — Meta](https://developers.facebook.com/docs/graph-api/webhooks/getting-started)
- [Коллекция Instagram API от Meta в Postman](https://www.postman.com/meta/instagram/overview)

Прямые страницы Meta вернули ошибку доступа в среде исследования. Официальная коллекция Meta в Postman частично доступна и различает Instagram Login и Facebook Login, но полную актуальную процедуру подключения подтвердить здесь не удалось. Поэтому OAuth, отправка, выбор версии Graph API и готовность прав доступа **не заявляются реализованными или проверенными**. Не переносить права из Facebook Login в Instagram Login автоматически.

Подготовлен входящий адаптер для текстовых событий `object=instagram`, `entry[].messaging[]`: account-scoped проверка получателя, `message.mid`, `sender.id`, игнорирование `is_echo`; проверка HMAC-SHA256 над исходными байтами тела (`X-Hub-Signature-256`), GET challenge с отдельным verify token. Криптография и обработка записанных тестовых событий проверены локально; контракт должен быть повторно проверен на актуальном официальном webhook-примере перед реальным подключением.

Понадобятся профессиональный аккаунт владельца, приложение Meta с настроенным Instagram Login, его App Secret, разрешения на управление сообщениями по выбранному пути, access token, Instagram account ID, версия API из текущей документации и HTTPS callback. Точные требования к review, уровням доступа, тестовым ролям и окну ответов проверить в документации и кабинете именно этого приложения до подключения. Сейчас никакая версия API не зафиксирована вымышленным значением, токены не используются для исходящих запросов.

## Как проверить адаптеры сейчас

Самый простой путь: панель → «Адаптеры / тесты». Отправьте встроенное JSON-событие дважды: второй результат содержит `duplicate: true`, заявка и исходящий ответ не дублируются. После «Обновить» видна очередь; «Имитировать ошибку сервиса» и «Повторить в симуляторе» изменяют только демонстрационный статус.

Тестовые примеры хранятся в `docs/events.json`. Демо-endpoint доступен только авторизованной команде с CSRF-токеном. Демо-идентичности отделены от реальных префиксами каналов.

Для проверки локального HTTP webhook: установить `WEBHOOKS_ENABLED=true` и секреты в `.env`, перезапустить, передать JSON с правильным заголовком. Сервер доступен только на localhost. Это не регистрация webhook у платформы. Не открывать этот `http.server` в интернет через туннель. Перед публичным подключением заменить HTTP-обвязку на production-сервер, добавить HTTPS, Secure-cookie, доменный allowlist, ограничение размера очередей, устойчивые сессии, роли сотрудников и мониторинг.

## События и статусы

`lead_saved` выставляется после успешной транзакции. `manager_notified=false` и `consultation_confirmed=false` в этом прототипе всегда. Статус «передана менеджеру» означает помещение в локальную очередь ручной обработки, не внешнее уведомление. `demo_not_sent`, `demo_error`, `demo_delivered` не означают реальную доставку.

Дедупликация входящих событий реализована. Полная гарантия единственной внешней доставки не заявляется. Оповещения менеджеру, календарь и подтверждение консультации относятся к следующему этапу и требуют конкретного сервиса и внешних доступов.
